Accounts & providers

/agent/docs/accounts-and-providers/

Accounts

Accounts can be managed either in the TUI or via ~/.config/choreographr/accounts.toml.

In the TUI, press Ctrl+A to open the accounts page, then n to add an account (choose a provider, name it, and paste its API credential). See the quick start for the full walkthrough.

If you prefer to edit the file directly, accounts are configured via ~/.config/choreographr/accounts.toml. Account names must be lowercase alphanumeric with hyphens or underscores ([a-z0-9_-]). Each session may have its own account, set via /account <name>; there is no global default account.

[[account]]
name = "main"
provider = "openai"

[[account]]
name = "claude"
provider = "anthropic"

[[account]]
name = "gemini"
provider = "google"

[[account]]
name = "local"
provider = "ollama"
base_url = "http://localhost:11434/v1"
streaming = false
retry_max_attempts = 3

Adding API keys

Keys can be managed in the TUI — on the accounts page (Ctrl+A), select an account and press c to enter its API credential.

Alternatively, add a key for the service the account uses with the slash command:

/add-key openai sk-...

Keys are encrypted per-credential with the daemon's public key before being stored. The daemon starts locked — use /unlock to decrypt credentials into memory, and /lock to clear them again.

Providers

Choreographr supports 200+ providers across three wire protocols:

  • OpenAI-compatible — OpenAI, DeepSeek, Mistral, xAI, Groq, Together AI, OpenRouter, Hugging Face, GitHub Models, NVIDIA NIM, Cerebras, Fireworks AI, Alibaba (Qwen), Moonshot AI (Kimi), Perplexity, Z.ai, Ollama, LM Studio, and many more.
  • Anthropic Messages — Anthropic Claude, MiniMax, Vercel AI Gateway, Kimi Code, and more.
  • Google Generative AI — Google Gemini.

The provider/model catalog is built from models.dev plus policy overlays that supply everything models.dev can't express. Adding a new OpenAI-compatible provider needs no client code.

Catalog overlays

The catalog is assembled in three layers, lowest precedence to highest:

  1. models.dev base — the provider/model information. A normalized snapshot (catalog.bin) is compiled into the binary as the built-in fallback, while the daemon keeps a live copy regenerated from models.dev at runtime (cached on disk and re-fetched when stale; the embedded snapshot is used when no live copy is available). It includes the following information: context windows, output limits, reasoning support and levels, vision/image modalities, temperature, and deprecation.
  2. Built-in overlay — catalog/models-overlay.toml, compiled into the binary and merged at load time. It carries everything models.dev can't express: wire-protocol selection, endpoint policy, per-model exceptions (e.g. Anthropic tool_loop passback pins, Responses-API flags), and the local/niche providers models.dev doesn't cover (defined wholesale with their full model lists).
  3. User overlay — ~/.config/choreographr/models-overlay.toml, optional and sharing the same schema, merged last so it wins. Use it to fix or extend the catalog without rebuilding. It is watched live (alongside accounts.toml): edits reload on change, deleting it falls back to the two built-in layers, and /refresh-models re-reads it too.

An overlay is a TOML file: add a [provider.<slug>] table for each provider you want to change, and a [provider.<slug>.models."<model-id>"] sub-table for each model. Create and edit models-overlay.toml freely; any key not listed below is ignored with a warning.

Overlay schema

Provider scalar keys ([provider.<slug>]), all optional:

KeyTypeMeaning
protocolstringWire protocol: "openai", "anthropic", or "google"
max_tokens_fieldstringOpenAI protocol only: "max_completion_tokens" (default) or "max_tokens"
base_urlstringAPI base URL
default_modelstringModel used when no account/session model is set
display_namestringHuman-readable name (only needed for providers not in the base)

Per-model keys ([provider.<slug>.models."<model-id>"]), all optional:

KeyTypeMeaning
context_windowintegerContext window in tokens (0 = unknown)
max_output_tokensintegerOutput-token ceiling (0 = unknown)
reasoning_supportedbooleanWhether the model does reasoning
reasoning_levelsarray of stringsReasoning-effort slugs (e.g. ["off", "low", "high"])
responsesbooleanWhether the model uses the OpenAI Responses API
reasoning_passbackstringHow reasoning is echoed between turns: "none", "tool_loop", "all_turns", "signature", or "response_id"
reasoning_content_requiredbooleanWhether every request must carry a reasoning_content field (DeepSeek/GLM chat)
supports_visionbooleanWhether the model accepts image input
supports_image_outputbooleanWhether the model generates images
temperaturebooleanWhether the model accepts a temperature parameter
deprecatedbooleanLifecycle status

Merge semantics

  • Provider scalars are replaced field-by-field; any key you omit falls through to the lower layer.
  • Per-model entries are keyed by (provider, model id). Naming a model replaces only the fields you set onto the existing entry — everything you don't mention stays intact — and adds the entry if the model is new.
  • New providers (a [provider.<slug>] table absent from the base) are created wholesale: give them display_name, protocol, base_url, default_model, and their models.
  • Unknown keys are warned and skipped, never fatal, so a typo can't break the daemon.

Example user overlay 

# Patch policy and catalog information for a provider that already exists.
[provider.deepseek]
max_tokens_field = "max_completion_tokens"
default_model = "deepseek-v4-pro"

[provider.deepseek.models."deepseek-v4-pro"]
context_window = 131072
reasoning_supported = true
reasoning_levels = ["off", "low", "high"]
reasoning_passback = "tool_loop"

# Define a provider models.dev doesn't list (created wholesale).
[provider.my-gateway]
display_name = "My Gateway"
protocol = "openai"
base_url = "https://gateway.example.com/v1"
default_model = "my-model"

[provider.my-gateway.models."my-model"]
context_window = 65536
supports_vision = true

Account overrides

Every field has sensible defaults from the provider catalog and can be overridden per-account:

FieldDescription
base_urlAPI base URL
streamingEnable/disable streaming responses
retry_max_attemptsMax retry count on transient errors
retry_initial_backoff_msInitial backoff between retries (ms)
retry_max_backoff_msMax backoff between retries (ms)
connect_timeout_secsTCP connect timeout
request_timeout_secsHTTP request timeout
default_request_formatRequest format: "chat_completions" or "responses"
programmatic_tool_callingEnable programmatic tool calling (Responses API, gpt-5.6+)
context_windowDefault context window for all models

The Responses API is fully supported — including tool use, streaming, reasoning effort slugs, multi-turn chaining via previous_response_id, and programmatic tool calling (gpt-5.6+ models).

Image generation

The generate_image tool resolves its provider from the session's account. OpenAI-compatible accounts use the OpenAI Images adapter (gpt-image-*), and z.ai / Zhipu accounts use glm-image; the model is chosen from the provider's catalog image-output entries.
